### F1 — A failed dead-letter transfer can lose the original work

`toDLQ` logs a producer error but returns no success/failure result (`pkg/broker/consumer.go:196–208`). Both poison-envelope and exhausted-handler paths then return `"dlq"` (`:155–158,190–193`). The run loop counts that outcome and reaches `CommitUncommittedOffsets` regardless (`:116–125`). If publication fails while the consumer can still commit—for example a DLQ-specific authorization/availability failure—the source offset can advance with neither a committed business effect nor a durable DLQ record. Replaying the DLQ cannot recover a record that never arrived there.

The reviewer test injects handler failure and an unavailable franz-go producer. Its context remains live; the observable result is:

```text
ERROR DLQ produce failed error="no partitions available ... connect: connection refused"
reported dlq success despite failed DLQ publication; Run can commit the source offset
```

The probe proves the failure is swallowed and the outcome misreported. The potential source-offset loss is established by the following unguarded commit in source; it was not reproduced against live broker offsets. The transactional outbox/inbox implementation remains valuable, but does not close this separate source-consumer/DLQ boundary. The design's no-loss promise is too strong (`docs/adr/ADR-004-messaging-outbox-inbox.md:24,42,56`).

### F2 — Accepted coordinates exceed Redis GEO's operating range

The challenge and `Point.Validate` accept latitude −90 through 90 (`pkg/geo/geo.go:23–31`). The projection performs `HSET` including the new version **before** `GEOADD` (`services/dispatch/internal/adapter/redis/redis.go:30–32`). For latitude 89, the exact submitted script produces:

```text
Apply attempt 1: ERR invalid longitude,latitude pair 0.000000,89.000000 ... @user_script:6
Apply attempt 2: 0
Stored driver hash: version=1, status=AVAILABLE, lat=89, lng=0
GEO entry count: 0
```

The failed script does not roll back its earlier hash mutation. Retry sees the new version and silently skips the absent GEO entry. The same accepted pickup latitude is passed directly to `GEOSEARCH` (`:63–72`), which cannot search it; the orchestrator treats search errors as no candidates and leaves the ride waiting (`services/dispatch/internal/usecase/orchestrator.go:377–407`). This requires a compatible fallback/index for the full allowed coordinates and failure-safe projection updates. Narrowing validation alone would change the brief's accepted range.

The two AC losses have distinct grounds: AC-03 cannot reliably use a valid latest driver location, and AC-04 cannot match around a valid pickup. Creation/retrieval and coordinate validation themselves remain correct, so AC-01 retains full credit. No additional idempotency penalty is taken for the same partial projection.

## Strengths

- Atomic claims are enforced by the authoritative PostgreSQL driver row and exercised with real concurrent transactions (`services/driver/internal/adapter/postgres/postgres.go:79`; driver integration `:64`).
- State, inbox/outbox and audit writes share local transactions; matching decisions stay separate from transport/storage (`pkg/pgutil/pgutil.go:120`; `services/dispatch/internal/domain/match.go:32`).
- Offer ownership, permanent exclusions, timeout and rematching have substantial automated evidence (`services/dispatch/internal/usecase/orchestrator_integration_test.go:212,261,330`).
- Scale analysis, ADRs, traceability, structured logs and useful metrics are concrete and connected to code (`docs/scalability.md:62`; `pkg/obs/log.go:84`; dispatch metrics `orchestrator.go:40`).

## Key Risks

- Unprocessed records can be skipped when DLQ publication fails; manual replay cannot recover a missing DLQ record, F1.
- Valid polar coordinates can be accepted and persisted while projection/matching cannot use them; retry may silently preserve partial state, F2.
- Relay ordering assumes one instance; scaling replicas requires leader election or CDC (`docs/architecture.md:483`). This is disclosed and not confused with current driver exclusivity.
- After retry exhaustion, post-pivot commands may need manual DLQ replay; the resumer scans STARTED/RESERVING/MATCHING/waiting states, not every ACCEPTED/terminal participant effect (`services/dispatch/internal/usecase/offers.go:227`; dispatch adapter `postgres.go:136`). The README discloses manual replay; it is not an unlimited automatic retry guarantee.
- Redis rebuild after runtime loss, inbox/outbox retention, polling per stream and capacity testing are disclosed future work (`docs/architecture.md:481–489`). No load-test or production-infrastructure requirement is added.

## Improvements

1. Make DLQ publication return an error and advance source offsets only after handler commit or confirmed durable DLQ transfer. Test failed producer/ACL/timeout cases, including restart and replay.
2. Preserve the brief's full coordinate range with a compatible candidate-search fallback or index. Ensure projection failures cannot publish the new version ahead of the actual GEO mutation, and test retry after partial script failure.
3. Add failure-focused broker and saga tests around unavailable DB/broker, stale replies and post-pivot recovery. Keep SQL race tests and promote the reviewer's passing accepted-ride cancellation flow into a permanent e2e regression.
4. Make the Redis integration container wait for its external port as well as its ready log; separate application failures from local engine-forwarding readiness failures.
5. Retain the documented single-instance boundary until relay leader election/CDC and projection rebuilding are implemented. Prioritize those correctness guarantees over expanding optional interfaces.

Close the failed-DLQ acknowledgement gap and the coordinate/projection mismatch to make its reliability claims match the delivered behavior.
